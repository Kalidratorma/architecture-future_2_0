# Task1 (C4: Containers, проблемы и приоритизация)

---

## Проблемные места (как есть)

1. **Монолитная логика в DWH (MS SQL 2008)**
    - Жёсткая связка источников/витрин, низкая изменяемость, дорогие изменения.
    - OLTP/операционка и аналитика спутаны в бизнес-логике ETL.
    - Зависимость от устаревшей версии, ограниченные возможности масштабирования.

2. **Огромные объёмы данных и долгие трансформации**
    - Сотни терабайт, тяжёлые ETL/ELT, отчёты формируются часами.
    - Нет выделенной compute-платформы под распределённые обработки.

3. **Нет доменных границ и «data ownership»**
    - Финтех, клиники, фарма, электроника — всё стекается в общий DWH.
    - Любое изменение в одном домене может повредить другим.

4. **Старая интеграционная шина (Apache Camel) как «бутылочное горлышко»**
    - Преимущественно point-to-point и batch; нет событийной модели.
    - Сложно масштабировать и отслеживать сквозную доставку.

5. **BI поверх DWH с кастомизациями**
    - Хрупкие отчёты, повторная логика, «скрытые» бизнес-правила в визуальных слоях.
    - Нет единого семантического слоя (metrics-as-code, единые определения KPI).

6. **Разнородный технологический зоопарк без единой платформенной опоры**
    - Python/Go/Java/Power* + SQL 2008 + старая ESB, нет нормальной дата-платформы.
    - Нет единой политики безопасности/доступов/маскирования.

7. **Управление данными и соответствие требованиям (PII/PHI/финданные)**
    - Недостаточно зрелая политика классификации, маскирования, lineage, DLP.
    - Риск смешения PHI/PII с аналитикой; сложности с аудитом.

8. **Отсутствие прозрачной каталогизации и lineage**
    - Пользователи не знают «источник правды», долго ищут наборы.
    - Трудно расследовать проблемы качества.

9. **Слабая наблюдаемость (observability) и SLO для data-потоков**
    - Нет общих метрик задержек, потерь, пропускной способности; нет алёртинга.

10. **Миграция в новые бизнесы требует «дописать DWH»**
    - Низкая time-to-market: каждый новый домен упирается в расширение общедоменного DWH.

## Приоритизация (MoSCoW)

### Must (обязательно)
- **Доменно-ориентированная архитектура данных (data mesh-подход)**: явные домены (Финтех, Клиники, Фарма, Электроника), «data products» с чёткими SLA/контрактами.
- **Единая дата-платформа для хранения и вычислений (Lakehouse/объектное хранилище + распределённые вычисления)**.
- **Событийная интеграция между доменами** (event streaming) + CDC из источников.
- **Единый слой управления данными**: каталог, классификация, доступы, маскирование PII/PHI, lineage.
- **Семантический слой для BI/self-service**: единые определения метрик, доступ по ролям.
- **Разделение PHI/медданных**: исключить медицинские карты/исследования из аналитической витрины (только агрегаты/обезличенные данные по правилам).
- **Наблюдаемость и SLO для data-потоков**: метрики, трассировка, алёрты, аудит.

### Should (желательно)
- Постепенная **де-композиция логики из DWH** в доменные пайплайны/модели.
- **Backfill исторических данных** в lakehouse, оптимизация хранений (партиционирование).
- **Стандартизация ETL/ELT** (шаблоны, CI/CD, тестирование данных).
- **Переезд ключевых отчётов** на семантический слой, сокращение кастомизаций в BI.

### Could (можно)
- Реал-тайм KPI/дашборды для части доменов (финтех, телеметрия оборудования).
- A/B-платформа, фичехранилище (feature store) под ИИ.
- MDM/Golden Records в приоритетных сущностях (клиент/счёт/организация).

### Won’t (в этот год)
- Полный отказ от Power Builder/всех легаси-отчётов.
- Миграция *всех* отчётов и сценариев — только приоритетные.
- Полная замена всех интеграций Camel — замена итеративная, по доменам.

## Диаграмма контейнеров (состояние через год)

Файл: [`container.puml`](./container.puml) (C4-PlantUML).  
Ключевые контейнеры:
- **Self-Service Data Portal** (витрина/портал) + **Semantic Layer** (единые метрики).
- **Data Platform (Lakehouse Storage + Compute)** — единая платформа для доменов.
- **Streaming Platform** (event bus) и **CDC Ingestion**.
- **Data Governance & Catalog** (каталог, политика доступа, маскирование, lineage).
- **Domain Data Products** (Finance, Clinics, Pharma, Med-Electronics) — каждая команда отвечает за свои наборы/каналы/модели и публикует контракт.
- **AI/ML Platform** (отдельно от портала; PHI — только в закрытых границах).
- **Legacy DWH** (MS SQL 2008) и **Legacy BI** — остаются в отдельных доменах как временные источники.
- **Observability Stack** (метрики/логи/трассировка).
- **Security & IAM** (RBAC/ABAC, KMS/Vault).

**Важные принципы:**
- Медкарты/исследования **не** входят в витрину. Для аналитики — только агрегаты/обезличивание по правилам домена.
- Все новые данные публикуются как доменные продукты через событийную/табличную контрактную модель; «общего DWH для всех» больше нет.

## Пояснения к взаимодействиям

- Источники (финтех-сервисы, клиники, фарма, телеметрия оборудования) отдают события/CDC-потоки → **Streaming Platform / Ingestion** → **Data Platform**.
- Каждая доменная команда строит **собственные пайплайны** (ETL/ELT), хранит **свои слои** (raw/curated/serving) и публикует **data products**.
- **BI/Portal** обращается не напрямую к «сырым данным», а к **семантическому слою** и/или опубликованным доменными продуктами витринам.
- **Governance & Catalog** обеспечивает поиск датасетов, доступы, маскирование, lineage, data quality и аудит.
- **Legacy DWH/BI** работают параллельно; отчёты постепенно переносятся в новый слой.
- Для ИИ-сервисов чувствительные данные остаются в соответствующем домене; для кросс-доменных задач применяются обезличивание/агрегации.

## Что считать результатом этапа (через год)
- Портал самообслуживания с ролями и семантическим слоем.
- Доменные data products (минимум для Финтех и Клиник), контрактная публикация.
- Каталог/lineage/управление доступом и маскированием.
- Основные интеграции переведены на CDC/события; Camel постепенно вымывается.
- Legacy DWH локализован в отдельный домен, критичные отчёты — перенесены.
